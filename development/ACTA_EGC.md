## 5. Política de gestión de ramas

El equipo utilizará **EGCFlow**, el modelo de uso del repositorio establecido para la asignatura. Se mantendrán dos ramas permanentes:

- **`trunk`:** será la rama de integración del equipo. En ella se incorporarán con frecuencia los cambios terminados. Deberá mantenerse en un estado razonable para que el proyecto pueda construirse, las pruebas básicas puedan ejecutarse correctamente y el resto del equipo pueda continuar trabajando a partir de ella.
- **`main`:** representará la línea de entregas. Cuando `trunk` alcance un estado suficientemente estable para una entrega, se incorporará ese estado a `main` y se identificará mediante una etiqueta (*tag*) de versión (por ejemplo, `1.0` o `2.0`).

El trabajo se organizará mediante **ramas de tarea**, cada una asociada a un propósito concreto, como una funcionalidad, corrección, mejora de documentación o refactorización. Se evitarán las ramas personales: el nombre de cada rama deberá describir el cambio que contiene.

Como acuerdos de trabajo:

1. Antes de comenzar una tarea, se creará una rama específica a partir de `trunk`.
2. Mientras la rama de tarea permanezca abierta, se mantendrá razonablemente sincronizada con `trunk` para reducir los problemas de integración.
3. Cuando la tarea esté terminada, sus cambios se integrarán en `trunk` utilizando Git, comprobando el resultado y resolviendo los posibles conflictos.
4. Una vez integrada y comprobada la tarea, se eliminará su rama. No se mantendrán ramas antiguas sin un propósito activo.
5. La tarea, su rama y los commits relacionados se vincularán, cuando corresponda, con la incidencia o elemento de trabajo registrado en GitHub Issues.
6. Los commits deberán ser claros y describir de forma concreta los cambios realizados.
7. Las integraciones en `trunk` deberán dejar el proyecto en un estado coherente, con la construcción y las pruebas básicas funcionando.
8. **No se utilizarán pull requests para integrar cambios entre ramas del propio equipo.** La integración se realizará directamente con Git, como establece EGCFlow. Los pull requestso se reservarán para proponer cambios al proyecto de otro equipo o recibir contribuciones desde otro equip.

Las etiquetas de versión se utilizarán para identificar los estados de `main` correspondientes a las entregas. Cualquier ajuste operativo deberá respetar este modelo y las indicaciones del profesorado.
